## Defects, limitations, and follow-up

The historical blocker was MongoDB Memory Server startup on this Windows host: the pre-existing archive failed MD5 verification, while a separate freshly downloaded archive reached `mongod` startup but failed with an internal `fassert()` error. On 9 November, the Codex sandbox's MongoDB-to-API loopback returned `EACCES`; the API exited and no frontend listener remained. Subsequent host-Windows Chrome sessions on 9–10 November produced the screenshots and observations in the current matrix. Remaining gaps are successful registration/verification, staging email delivery, a completed reset-token flow, TC-OE-010 load/availability evidence, and exhaustive keyboard/accessibility/browser coverage. The 10 November registration request returned 503 and displayed an error; the screenshot does not establish why.

No further attempt in the Codex sandbox is needed to repeat the host-browser scenarios already evidenced. If successful email-dependent registration or password reset is required for final acceptance, configure an approved staging mail service and disposable mailbox, capture delivery without exposing credentials or tokens, and complete the verification/reset links. Investigate the 503 using authorized server-side logs/configuration before attributing a cause. Run TC-OE-010 with a controlled test environment if performance and availability evidence is required. Keep SMTP delivery unverified until real staging delivery is observed.
